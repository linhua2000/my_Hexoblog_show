先选芯片，再拧螺丝：一台麦轮机械臂小车的系统总览与复刻路线

发表于2026-10-31|更新于2026-10-31|项目记录
|浏览量:

先说结论：比赛车不是模块的堆叠，而是接口、时序和标定的系统。

单看每个模块，电机能转、编码器能读、陀螺仪能出角度、舵机能到位、视觉能发帧；可一旦把它们按 5 ms 的节拍串起来，任何一处接口不一致，最后都会表现成「车在起点歪了两厘米，机械臂在终点抓了个空」。

这篇文章想带你从零看一遍这台车：它由什么组成、控制是怎么跑起来的、复刻应该按什么顺序走、每一步怎么验收、卡住了先查哪里。

视频记录：广东省工科大学生实验综合技能竞赛记录

在正式动手之前，我先讲一个小故事。

0. 最后留在车上的，不是最新代码

2026 年 10 月 10 日，这个项目连续提交了八次。

提交说明从「能跑全程差，标定两个角度」，到「更新了视觉的一个标定大致能跑个全程」，再到「能跑大概全程」，最后是「能完整满分，但待调速」。

然后，下一条是：

这一版有 bug，还是使用满分稳定的吧。

也就是说，最后真正留在车上的，不是最新代码，而是被主动回滚的那一版。

这条提交比任何一张满分照片都更能说明比赛车的本质：最新代码不等于最稳代码。 比赛前应该有一个 known-good 版本（固件 + 参数备份），每次改完都能退回去。仓库最后选择「满分稳定版」，不是保守，而是工程判断。

0.1 我为什么用教程的方式写它

动手写这套笔记之前，我有两段别的项目经历。

第一段是调一辆两轮平衡小车。那是一篇个人向的调参记录，我最大的收获不是某个参数值，而是顺序：先极性、后大小；先直立环、后速度环。 还有一个更隐蔽的教训——姿态读取耗时较长，读取过程一旦被更高优先级的中断打断，角度环拿到的就是「滞后、不连续」的角度，车会莫名发抖。参数怎么调都不对时，问题往往根本不在参数。

第二段是 2026 年电赛校赛的 C 题（单目测距），拿了校赛二等奖。那一个月让我记住两件事：

  1. 先搭出来，再解决问题。 不要一开始就追求完美，先用最简单的方法把功能跑通；
  2. 信任队友很重要，但自己的判断和主动推进同样重要。 我早就知道陀螺仪依赖初始摆放，却因为「方案够用了」而没有立刻去改；循迹模块也是拖到最后两三天才写出来。后来证明，它确实让车更稳。

这两段经历正好对应这台车的两条主线：5 ms 节拍要干净，复刻顺序要先骨架后细节。

说明：平衡小车和 2026 电赛校赛是另外两个项目。下面提到它们，只是借用那两次踩坑的方法和心态，不代表这台车参加过那些比赛。

0.2 写给谁、花多久、怎么读

这篇适合有基础的新手：

  • 会 C，写过 STM32，至少点过灯、配过串口；
  • 用过 CubeMX 和 HAL，但不一定独立做过完整的小车项目；
  • 想照着做一台，或者想看懂这类比赛车的工程结构。

不要求你会麦轮运动学、串级 PID、串行总线舵机——这些会在对应步骤里从「为什么」讲起。

时间上，只做底盘大约 12 周；含视觉和机械臂大约 46 周，取决于 3D 打印、装配和标定次数。下面的耗时都是经验估计，不是精确值。

每一节都按同一个节奏走：

预计耗时 / 前置 → 做到什么 → 跟着做 → 怎么验收 → 失败先查什么 → 踩坑记录

验收不过，不要进下一步。 这不是形式主义：底盘没走直就装机械臂、视觉没对准就调路线，后面所有的调试都会被前面的问题污染。

1. 先看全貌：这辆车由什么组成

1.1 一句话和四张能力卡

这是一台用 STM32F407 把四轮麦轮底盘、九轴 IMU、四自由度串行总线机械臂、视觉上位机和调试交互串起来的比赛车。

可以把它拆成四张能力卡：

  • 走：四个麦克纳姆轮、四路编码器、两片双 H 桥驱动；
  • 看：HWT905/JY61P 九轴模块 + 视觉上位机；
  • 抓：四个飞特（Feetech）串行总线舵机组成的机械臂；
  • 交互：OLED、四个按键、激光、蓝牙日志。

1.3 两个必须记住的坑

第一，电机不是 CAN 电机。 工程里 CubeMX 确实初始化了 CAN1/CAN2，但应用层没有任何收发代码。这套车用的是双 H 桥驱动 + PWM，CAN 是早期预留。

第二，轮号不是空间顺序。 Wheel1 是左后，Wheel2 是左前，Wheel3 是右前，Wheel4 是右后。调增益、看日志时如果按「顺时针 1234」去理解，一定会混乱。这个映射在 mailuncontrol.h 顶部写死了。

轮号 实际位置 编码器定时器 PWM
Wheel1 左后（B 轮） TIM1 PB14
Wheel2 左前（A 轮） TIM3 PB15
Wheel3 右前（B 轮） TIM2 PB8
Wheel4 右后（A 轮） TIM4 PB9

对角同型号：左前 = 右后 = A 轮，左后 = 右前 = B 轮，是标准麦轮 X 布局。

每层只做一件事：HAL 管寄存器、时钟和外设初始化；Middle_Drivers 做硬件封装和核心控制；SCSLib 是隔离出来的第三方舵机协议栈；app 只做任务编排。

好处是：换板子主要改 HAL 和 Middle_Drivers 的引脚，换路线只改 app/control.c 的参数表。

1.5 三条接口契约

复刻时真正容易出错的，不是某个算法写不出来，而是模块之间的约定没对齐。这套工程有三条契约，后面每一步都会反复提到。

契约 内容 典型位置
单位 车体速度用 mm/s、rad/s；运动学输出 RPM；速度环用脉冲/5 ms；电机输出 ±1050 kinematics.h、mailuncontrol.h、motor.h
符号 +x 车头，+y 左侧，θ 逆时针为正 kinematics.h、odometry.c
时序 编码器 → 里程计 → 状态机 → 逆解 → 速度环 → 电机，顺序不能乱 app/control.c 的 TIM6 回调

这三条里，单位错会导致「车走但走不准」，符号错会导致「车往反方向走」，时序错会导致「指令晚一拍生效」。三类现象看起来都像控制参数没调好，实际根因完全不同。

2. 5 ms 一拍：整车怎么跑起来

2.1 TIM6 中断链

整车的控制主节拍是 TIM6 的 5 ms 中断。每一拍做六件事，顺序固定：

    sequenceDiagram
    participant T as TIM6 (5ms)
    participant E as Encoder
    participant O as Odometry
    participant S as StateMachine
    participant K as Kinematics
    participant P as Speed PI
    participant M as Motor

    T->>E: Encoder_Update()
    T->>O: Odometry_Update()
    T->>S: StateMachine_Update()
    S->>S: Set_Vel(vx, vy, ω)
    T->>K: Exp_Speed_Cal()
    T->>P: Velocity_Wheel1..4()
    T->>M: Motor_Load()

图 5：5 ms 数据流

顺序为什么不能乱：

  1. 编码器先采样，里程计这一拍才有增量；
  2. 里程计先更新，状态机才能用最新的 odometry.x / y / theta 做判据；
  3. Set_Vel() 只是把目标存进 kinematics.exp_vel，不做任何解算。它必须在 Exp_Speed_Cal() 之前调用，否则这一拍算的还是上一拍的指令；
  4. 速度环的目标和反馈都是「脉冲/5 ms」，由 Kinematics_RPM_To_Pulse() 从 RPM 转换过去；
  5. 限幅在 Motor_Load() 内部，把 PWM 夹到 ±1050。

还有一个容易忽略的细节：如果这一拍不跑状态机，代码必须显式写 Set_Vel(0, 0, 0)。因为 Exp_Speed_Cal() 每拍都会拿上一拍的值解算，光是不调状态机是停不住车的。

2.2 主循环做什么

主循环不是「空转等中断」。它负责那些不需要 5 ms 精度、但可能耗时长的事：

  • Hold_Action_Update()：机械臂动作状态机，每圈调用一次；
  • OLED 每 200 ms 刷新一次；
  • 日志和调试回传；
  • 激光、识别直线等独立测试；
  • 按键事件的消费端。

机械臂为什么不放进 5 ms 中断？因为 WritePosEx() 是阻塞发送，发一帧大约毫秒级；而一个舵机动作从几百毫秒到几秒不等。把它塞进 5 ms 中断，会直接打乱控制节拍，车轮会一顿一顿地走。

这和我调平衡小车时遇到的是同一类问题：姿态读取耗时且不能被更高优先级中断打断，就绝不能随便塞进控制节拍里。中断里只放确定、短小、可预期的事。

2.3 两种握手

底盘和另外两个子系统之间，各有一套握手。

底盘 ↔ 机械臂：状态机只设置 hold_action_id（要执行哪一段动作）和 hold_action_state = RUN；主循环的机械臂状态机执行完，把状态置为 DONE；底盘看到 DONE，再进入下一个状态。

底盘 ↔ 视觉：底盘通过 Vision_Send_B6(cmd) 发请求，视觉回 A5 帧；收到新帧后置 vision_data 里的对应 flag，使用方读完自行清零。

握手的意义不是「礼貌」，而是让两个不同节拍的模块知道对方做完了没有。没有握手的系统，通常会在调试时表现成「偶尔提前一步」或「偶尔多做一次」。

3. 复刻路线：跟着做 11 步

这一节是全文的核心。不要一口气把所有模块都接上，按下面十一个步骤走，每一步都有可观察的验收标准。

S1S3 是方案与结构，决定这台车长什么样、能装下什么；S4S11 是软件与联调，决定它能不能稳定跑完。

先做最小闭环。 如果时间只够做一台能动的车，按 S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8 → S9 走完，先不碰视觉和机械臂。S10、S11 是后加的——底盘走得稳，它们才有意义。

S1：芯片选型

预计 0.5 天 ｜ 前置：无

做到什么：先把自己的需求数成外设，再拿这张清单去选芯片。

跟着做：

  1. 列出需要的定时器：4 路编码器 + 4 路独立 PWM + 1 个系统节拍；
  2. 列出串口：IMU、舵机、视觉、蓝牙，再加预留；
  3. 检查是否有浮点运算；
  4. 拿清单去对照候选芯片，打开 F407car.ioc 核对实际启用的外设。

这里要先说清楚：当时选 F407 并没有做一份正式的选型报告，理由很直白——F407 比 F103 更强，定时器更多，串口更多。下面这张表是事后按需求核对的，不是当时的决策记录。

需求 数量 常见 F103C8T6 F407VET6
编码器定时器 4 TIM1~4 全部占满 TIM1~4，仍有余量
独立 PWM 通道 4 无多余定时器 TIM10 / TIM11 / TIM12
串口 4 用 + 预留 3 个 USART 6 个
5 ms 系统节拍 1 通用定时器已被编码器占满 TIM6 独立
浮点运算 — 软件浮点 单精度 FPU
主频 / 存储 — 72 MHz / 64 KB + 20 KB 168 MHz / 512 KB + 192 KB

这张表以常见的 F103C8T6 为参照。F103VE 这类大容量型号外设更多，但同样没有 FPU，所以不能笼统地说「所有 F103 都不够」。

关键在于四个编码器定时器几乎吃掉了 F103C8T6 的全部通用定时器：速度环还要独立的 PWM，系统节拍还要一个定时器，四路串口也差一个。控制环里又全是 float，没有 FPU 就是软件浮点，5 ms 的节拍会变得很紧。

怎么验收：不看表也能说出「4 个编码器定时器、4 路独立 PWM、4 个在用串口」；能解释 F103C8T6 为什么排不开。

失败先查什么：把 F103C8T6 和 F103VE 混为一谈；只看主频不看外设数量；忽略 FPU；把「更强」写成没有依据的对比。

踩坑记录：没有选型报告不是光荣，但也不致命。关键是把需求数清楚——只要你能用一句话解释「为什么这块芯片排得开」，选型就是成立的。

S2：引脚分配与模块选择

预计 1 天 ｜ 前置：S1 完成

做到什么：先把模块列出来，再把每个模块的接口落到具体引脚，最后在 CubeMX 里生成工程。

跟着做：

  1. 先锁死不能动的：SWD（PA13/PA14）、晶振、调试串口；
  2. 编码器独占 TIM1~TIM4，不要一脚踩两只船；
  3. PWM 用 TIM10/11/12，不去抢编码器定时器；
  4. 四路串口按「IMU、舵机、视觉、蓝牙」排；
  5. 每接一个模块就先单独上电测通，再继续下一个。

模块选择这一步要坦白：手头有什么用什么。这不是缺点，比赛车本来就该优先用自己已经调通的模块，把时间花在联调上。但它有两个前提：规格够用，接口不打架。

驱动是「手头有什么用什么」的典型例子。实车用的是 D50A ×2，性能更好，但两块板体积大，对这台小车来说很占地方，装配和替换都麻烦。复刻建议用 TB6612 模块：它集成在一块小驱动板上，体积小、接线少，坏了整块换。两者的控制接口都是 IN1/IN2 + PWM，Motor_Load() 不用改。

怎么验收：引脚表里没有重复分配；四路编码器正转都为正；四路 PWM 能独立调速；4 路串口能同时收发；OLED、四个按键、激光都能单独测通；能指出这块板子上 PD11/PD15 存在板内短接。

失败先查什么：照抄旧分配表；encoder.h 里 TIM4 的注释还写着 PB6/PB7（已过期）；I2C1 和编码器抢 PB6/PB7；按键没上拉导致悬空；激光直驱电流不够；怀疑代码之前，先万用表量通断。

踩坑记录：TIM4 编码器最早接在 PB6/PB7 上，正好和 I2C1（OLED）抢引脚。把 TIM4 换到 PD12/PD13 之后，PB6/PB7 让给了 I2C1，PWM 也不必再和编码器共用定时器。这就是「先画一张引脚表」的价值——在 CubeMX 里点错一次，复刻的人就要拆线重焊。

S3：机械结构与装配

预计 2~4 天（含打印等待）｜ 前置：S2 完成

做到什么：打印底盘和机械臂，把臂装到底盘中左位置，调整配重，检查承力件。

跟着做：

  1. 打印底盘和机械臂，关键承力件加厚或换 PETG/ABS；
  2. 把机械臂装到底盘中左位置；
  3. 装电池，用手压四个角感受承重；
  4. 必要时挪电池配重；
  5. 机械臂全伸，复查四轮是否仍着地。

三句话先记住：

  • 几何中心不是重心。 臂装在中左之后，整车重心向左前偏，左前轮承重最大，起步更容易打滑；它会伪装成 Pos_Yaw 没调好。
  • 材料也会影响控制。 PLA 件长期受力会蠕变，表现为底盘塌、臂底座歪、孔位松。
  • 软件补不回偏载。 No_rear_wheels / No_front_wheels 只做前后替代，左右偏载只能靠臂位置、电池位置和配重改善。

怎么验收：四轮同时着地，压四角没有明显的跷跷板；机械臂全伸时车头不翘；低速直线起步时，左前轮不是最先打滑的那个。

失败先查什么：把所有打滑都归咎于 PID；四轮不等高；臂底座刚度不够；电池位置没拿来配重。

踩坑记录：左前轮承重最大，起步先打滑，很容易被误判成航向环没调好。先看结构，再看参数。

S4：规则与坐标

预计 0.5 天 ｜ 前置：S3 完成

做到什么：在纸上画出场地草图，标出起点、终点和障碍物；然后定义 +x、+y、+θ。

跟着做：

  1. 画一张场地草图；
  2. 标出起点、终点、障碍物；
  3. 写死 +x 车头、+y 左侧、θ 逆时针为正；
  4. 拿 kinematics.h 顶部的符号约定逐条对照。

怎么验收：纸上的方向和代码里的约定一致；你能不查代码就说出「命令左移时，vy 是正还是负」。

失败先查什么：左右手系混用；角度正方向写成顺时针；把「车体坐标」和「世界坐标」当成一回事。

踩坑记录：坐标符号是后面所有调试的公共语言。这里省下的半小时，后面会用几小时还回来。

S5：电源、驱动与单轮

预计 0.5~1 天 ｜ 前置：S4 完成

做到什么：共地、供电、驱动板接线（TB6612 或 D50A 均可）；把车架空，让单个轮子正反转。

跟着做：

  1. 电源共地；
  2. 驱动板接线；
  3. 把车架空，车轮离地；
  4. 给单轮正反转指令；
  5. 四轮同时正转，确认方向一致；
  6. 万用表量一遍 PD11/PD15 是否板内短接。

Motor_Init() 会在运行时重设 TIM10/TIM11/TIM12 的 PSC/ARR，把四路 PWM 统一到 20 kHz——CubeMX 里的定时器配置不一定是你想要的最终值。

怎么验收：给 1 号轮一个正指令，只有左后轮转，方向与指令一致；四个轮子同时正转时方向一致。

失败先查什么：电源没有共地；开发板上 PD11/PD15 存在板内短接；PWM 定时器挂在不同总线上（TIM10/11 在 APB2，TIM12 在 APB1），时钟源不同；ARR 设置与比较值量纲不一致。

踩坑记录：D50A 性能更好，但体积大；TB6612 小、接线少、坏了整块换。两者接口相同，代码不用改。选哪个，取决于你的结构和备件。

S6：编码器与四轮速度环

预计 1 天 ｜ 前置：S5 完成

做到什么：手转每个轮子，观察 5 ms 增量；再让速度环追一个固定目标。

跟着做：

  1. 手转每个轮子，观察 5 ms 增量；
  2. 确认正转时增量为正；
  3. 给阶跃目标，观察轮速响应；
  4. 记录增益改动的位置。

怎么验收：正转时增量为正，增速时增量线性变大；给阶跃目标时，轮速能跟上且没有持续振荡。

失败先查什么：轮号与定时器映射错；编码器边沿极性反；目标与反馈单位不一致；Target == 0 时积分没有清。

踩坑记录：仓库里保留了 #1 100 这类蓝牙调试命令的解析，但当前主控制通路并没有用 Debug_Target[] 驱动电机。想单轮测试，最直接的办法是临时在 Motor_Load() 处给常数，或者写一个只跑一次的小测试函数。

S7：麦轮解算与里程计

预计 1~2 天 ｜ 前置：S6 完成

做到什么：用 Set_Vel(vx, vy, ω) 分别让车前后、左右、原地旋转；再用手推车，观察里程计。

跟着做：

  1. 架空做前后、左右、原地旋转；
  2. 落地手推，观察 x / y / θ；
  3. 前推时 x 应增大，左推时 y 应增大，逆时针转时 θ 应增大；
  4. 记录一次两米直线的里程计误差。

怎么验收：前推时 x 增大，左推时 y 增大，逆时针转时 θ 增大；记录一次两米直线的里程计误差。

失败先查什么：八个符号宏（4 个 WHEEL_VY_SIGN_* + 4 个 WHEEL_WZ_SIGN_*）；轮距到底是「中心距」还是「半中心距」；YAW_SIGN 方向；陀螺仪第一帧还没到就开始积分。

踩坑记录：里程计假设「轮子不打滑」。一旦打滑，x/y 就会系统性偏大。参数再好，也补不回地面和结构的问题。

S8：位置环与单段行走

预计 1~2 天 ｜ 前置：S7 完成

做到什么：让车沿一条 1 米直线走。沿程轴给固定速度，横向轴用位置环按住，航向用 Pos_Yaw 锁在 0°。

跟着做：

  1. 先用 Pos_Yaw 锁住航向；
  2. 再用 Pos_Y 压住横向误差；
  3. 最后沿程轴给固定速度；
  4. 到点停住，量终点误差。

怎么验收：到点能停住；横向误差在设定容差内；航向没有持续跑偏。

失败先查什么：三个环的单位不同（x/y 是 mm → mm/s，yaw 是 deg → rad/s），Kp 数值不能横向比较；积分限幅太小导致顶死；Target == 0 的语义。

踩坑记录：三个环的 Kp 数值完全不可比。看别人的参数表之前，先看单位。

S9：十段路线空跑

预计 2~3 天 ｜ 前置：S8 完成

做到什么：把位置环装进状态机，按十段 MOVE/HOLD 走完整条路线。

空场地不接视觉、不装机械臂时，能跑到 SM_DONE 的是单路线调试通路 line_test()；完整通路 StateMachine_Update() 在 HOLD1、MOVE7、HOLD8、MOVE10 等视觉和机械臂握手，要等 S10、S11 接上才能走到底。

跟着做：

  1. 空场地先跑 line_test()；
  2. 逐段记录里程计与地面实测；
  3. 再上完整状态机，确认它会在视觉/机械臂段停住。

怎么验收：line_test() 用绝对坐标阈值，StateMachine_Update() 用「进入本段时的里程计位置 + 本段增量」判断出口；空跑用前者，逐段记录里程计与地面实测，最终出现 ST:DONE。

失败先查什么：长距离段车轮打滑；某段条件永远不成立，车一直往前开（MOVE 段刻意没有加超时兜底，上电前必须把车放好）；视觉段没有握手导致卡住；SM_DONE 没有出口，重跑要重新上电；改了一段参数牵连了上下游。

踩坑记录：路线参数用「进入点 + 本段增量」组织，改一段不会牵连上下游。但相对判据只解决参数互相牵连，不解决轮子打滑。

S10：串口感知与视觉

预计 2~3 天 ｜ 前置：S9 完成

做到什么：让陀螺仪稳定出帧，视觉帧能在 OLED 上看到；用按键模拟 A5、球帧、桶帧，推进对应流程。

跟着做：

  1. 确认陀螺仪稳定出帧；
  2. 在 OLED 上看到视觉帧；
  3. 用按键模拟 A5、球帧、桶帧；
  4. 拔插串口，验证能自动恢复。

怎么验收：OLED 能看到 turn_x / turn_y；按键模拟能让流程往前走；串口出错后能自动恢复，不需要按复位。

失败先查什么：帧尾不对或大小端理解错；HAL_UART_RxCpltCallback 在两个文件里重复定义，链接时只留一个，导致收完一帧不再重新武装；没有处理 ORE/FE/NE，串口一旦溢出就永久停摆。

踩坑记录：HAL_UART_RxCpltCallback() 在两个文件里各写一份时，编译能过、链接只留一个，结果某个串口收完一帧就不再重新武装。这种问题不会在编译期报错，只能靠「收一帧就停」的现象去反查。

S11：机械臂与全流程

预计 2~3 天 ｜ 前置：S10 完成

做到什么：先让单个舵机动作，再让单个 part 动作，最后跑全流程。

跟着做：

  1. 确认四个舵机 ID 和波特率；
  2. 让单个舵机动作；
  3. 让单个 part 动作；
  4. 跑全流程到 DONE。

怎么验收：四个舵机 ID 正确、扭矩能打开；每个 part 能单独完成；全流程能到 DONE。

失败先查什么：舵机 ID 或波特率不对；姿态常量用了旧文档的值；到位判断一直不成立（回读链路没开）；动作之间没有超时兜底。

踩坑记录：旧文档里的姿态值不一定可信。比如舵机姿态表里的 part1 姿态和当前代码就对不上，到位容差、激光时长也不同。以代码里的宏为准，不要直接抄表。

5. 三个「看起来能跑」的陷阱

硬件与结构的坑见 S2/S3，本节只讲合车之后才会冒出来的软件坑。

5.1 模块都对，系统不对

这是最常见的一类。每个模块单独测试都正常，一合起来就出问题。通常查这四处：

  • 单位不统一：车体速度是 mm/s，运动学输出是 RPM，速度环吃的是脉冲/5 ms。三者混用，现象是「车能走，但速度莫名其妙」；
  • 符号不统一：轮号、轮位、编码器方向、陀螺仪方向，四个东西各有一套正方向。建议画一张表，逐项打勾；
  • 时序不对：Set_Vel() 存了目标，但 Exp_Speed_Cal() 没在同一拍调用，指令会晚一拍；
  • **共享变量没加 volatile**：中断里写、主循环里读的量，编译器优化后可能读到旧值。

还有两个跨模块的隐蔽坑：板级短接会让硬件先于软件出错；HAL_UART_RxCpltCallback() 在两个文件里各写一份时，编译能过、链接只留一个，结果某个串口收完一帧就不再重新武装。

5.2 车能走，但走不准

第二类问题通常不是控制参数，而是状态估计。

  • 编码器里程计假设「轮子不打滑」。一旦打滑，x/y 就会系统性偏大；
  • 陀螺仪第一帧还没到就抓零点，航向从一开始就是错的。代码里用 odometry.ready 做闸门；
  • 长距离直线误差会累积。工程里有一个 Slip_Offset 修正量，用来补偿某一段的系统偏差，但它是现场标定值，不是通用常数；
  • 某些段落后轮容易打滑，代码用 No_rear_wheels / No_front_wheels 让同侧轮的数据互为替代，并让不可信的那一组退出速度环。注意替代不是清零——清零会让正解出来的 vx/vy 减半。

5.3 能跑一次，不能稳定跑

第三类问题最像「玄学」，实际上大多是握手和版本管理。

  • 视觉旧帧没有及时消费，状态机拿上一帧的数据做判断；
  • 视觉断线或超时后没有兜底，车停在原地等；
  • 机械臂动作没有超时，某个舵机卡住后整个流程不前进；
  • 改了一个「看起来更好」的参数，结果破坏了已经跑通的路径。

这就回到开篇那条回滚提交：最新代码不等于最稳代码。校赛复盘里，我印象最深的一条也是这个——很多时候不是方案不对，而是我们太晚才去验证自己的判断。比赛前留一个 known-good 版本，改坏了能退回去；发现某个问题被「够用了」压住时，尽早动手验证，而不是等到最后两天。

6. 工具、物料与安全

类别 内容
必备硬件 STM32F407 开发板、ST-Link、12 V 电池、降压模块、TB6612 模块 ×2（复刻推荐；实车为 D50A ×2）、MG513-P30 电机 ×4、麦轮 ×4、总线舵机 ×4、OLED、按键、激光、蓝牙模块
结构加工 3D 打印机、PLA 耗材（关键承力件建议 PETG/ABS 或加厚）、M3 螺丝、铜柱、热熔螺母
调试工具 架空支架、卷尺、胶带、记号笔、万用表、USB-TTL、备用驱动板 / 舵机 / 轮子
软件 Keil MDK、STM32CubeMX、SW 查看/切片软件、串口助手、飞特舵机上位机、视觉上位机（不在本仓库）
待确认 电池规格、电源分配（仓库中没有原理图和 CAD 源文件）

三件事比物料更重要：

  1. 先搭架空测试台。 车轮离地，才能安全地验证方向、编码器和速度环。落地跑之前，至少要做完 S5 和 S6；
  2. 装好后先找重心。 机械臂装完、电池放上去之后，用手压四个角感受承重；必要时挪电池来配重，别指望 PID 补偿偏载；
  3. 准备一个 known-good 备份。 固件、参数表、舵机姿态表各存一份，标注日期和「能跑到哪一步」。

安全提示：调试时手不要放在轮子附近；激光不要直射眼睛；电池要有保险或急停。

7. 收尾：一条流水线、13 个自检问题

整条复刻路线可以压成一条流水线：

S1 选型 → S2 引脚 → S3 结构 → S4 坐标 → S5 单轮 → S6 速度环 → S7 运动学 → S8 直线 → S9 路线 → S10 感知 → S11 机械臂。

先搭出最小闭环，再逐步接线、校准、联调。底盘走得稳，视觉和机械臂才有意义。

读完这篇，你可以用下面这张清单检查自己是否真的理解了这辆车：

  • 能按需求数清外设，并说清 F103C8T6 为什么排不开吗？
  • 能独立做出一张不冲突的引脚表吗？
  • 机械臂全伸时，四个轮子还都着地吗？
  • 能说出 +x / +y / +θ 的定义吗？
  • 能独立让单个轮子正反转吗？
  • 编码器正转时，增量是正的吗？
  • 手推两米，里程计误差大概多少？
  • 单段直线能到点停住吗？
  • 十段空跑能到 SM_DONE 吗？
  • 陀螺仪 ready 之前，车会动吗？
  • 视觉断线时，车会停吗？
  • 机械臂每个 part 能单独跑吗？
  • 有一个 known-good 版本可以回滚吗？

如果只能做一件事：先把重心和四轮着地弄对，再让车在两米内走直。

后续篇目会按这 11 步逐一展开：引脚分配、机械结构与装配、规则与坐标、驱动与单轮、编码器与速度环、运动学与里程计、位置环与直线、十段路线、串口感知与视觉、机械臂与全流程。等底盘部分写完，再补一篇整车联调与复盘。

安全再提醒一次：架空测试、手离轮子、激光不直射、电池有保险。高频剧烈抖动时立刻断电，别让电机和驱动替你交学费。

写这套笔记的另一个原因，是校赛复盘时留下的一个念头：同一个实验室不是对手，而是伙伴。把踩过的坑写清楚，希望后来的学弟学妹能少走一点弯路。

平衡小车（直立环 + 速度环串级调参）
这是一篇个人向的调参记录。我用 STM32F103C8T6 + MPU6050（DMP 解算） 把一辆两轮平衡小车从「根本站不住」调到「能稳定直立、能被推动后自己回正」。把过程整理成教程，是为了让后来的学弟学妹少走弯路——很多坑看起来是玄学，其实都是极性、时序和调参顺序的问题。 两轮平衡小车用的是串级 PID： 内环（直立环）：角度环，本质是 PD，让车「站住」。 外环（速度环）：本质是 PI，抑制小车缓慢溜走，让车「钉在原位」。 调参口诀一句话：先极性、后大小；先直立环、后速度环。 踩过的坑：姿态角度在哪读、别被打断mpu_dmp_get_data() 会通过 I2C 从 MPU6050 的 DMP 里读出解算好的姿态角（pitch / roll / yaw）。这个函数耗时较长（毫秒级），而且读取期间不可被打断——一旦在读取过程中被更高优先级的中断抢占，就会引入额外延时，角度环拿到的是一个「滞后/不连续」的角度，车会莫名发抖甚至失控。 我的做法是把它放在控制节拍的定时器中断里读取，并保证读取过程中不被更高优先级的中断打断： 123456789...
